# 岗位匹配与能力雷达计算方式

> 目标版本：`radar-v2`
>
> 文档状态：阶段 1 规则已冻结，等待阶段 2 实现
>
> 当前代码说明：生产代码仍使用 `radar-v1`；本文件描述的是后续开发必须实现和验收的目标规则，不代表当前代码已经完成改造。

---

## 1. 目标与边界

岗位匹配用于对比“岗位要求”和“当前简历中的可验证证据”，固定包含六个能力维度：

1. 技能：工具、语言、算法、技术栈、方法等。
2. 经验：参与、负责、主导等经历深度，不直接等同于最低工作年限。
3. 项目：项目参与程度、责任范围、完成和交付情况。
4. 成果：作品、论文、专利、证书、量化指标及其他可验证产出。
5. 教育专业：专业方向、课程背景以及与岗位的能力相关性。
6. 行业领域：行业背景、业务场景和领域知识。

岗位匹配同时包含两条独立结果：

- **能力评分**：表达当前简历证据对可评分岗位要求的覆盖程度。
- **硬性条件核查**：表达必须条件是否满足、明确不满足或无法确认。

硬性条件不得暗中扣减能力分。如果未来增加统一推荐指数，必须另立公开公式并展示调整原因。

---

## 2. 职责边界

### 2.1 AI 负责

- 从 JD 中提取独立、不重复的岗位要求。
- 判断要求所属维度、是否硬性、是否参与能力评分。
- 从限定枚举中选择重要度。
- 针对每条岗位要求从简历中查找证据。
- 普通能力维度从限定枚举中选择要求深度、证据等级和相关度；教育专业和行业领域改用背景要求与背景匹配档位。
- 返回可追溯的岗位原文和简历原文摘录。

AI 不得直接决定最终分数、维度权重、匹配状态、优势和差距排序。

### 2.2 后端确定性算法负责

- 校验 AI 输出是否合法、完整、不重复、可追溯。
- 将离散档位映射为固定数值。
- 计算单项分、维度汇总、权重、综合能力匹配分和状态。
- 派生硬性条件、能力差距与简历证据不足列表。
- 保证同一份结构化输入始终得到相同结果。

### 2.3 前端负责

- 展示后端计算结果，不重新推导业务分数。
- 分开展示要求数量、重要度合计、权重和分数。
- 展示每项结果的原文、档位和计算过程。
- 按评分版本安全展示历史数据。

## 3. 单项要求结构

每条岗位要求至少包含：

```ts
interface ScoringRequirement {
  requirementId: string;
  title: string;
  requirement: string;
  jobEvidence: string;
  dimension: 'skill' | 'experience' | 'project' | 'achievement' | 'education' | 'industry' | 'other';
  isHard: boolean;
  isScoreable: boolean;
  importance: 'core' | 'important' | 'normal' | 'bonus';
  requiredDepth?: 'basic' | 'familiar' | 'practical' | 'expert';
  resumeEvidenceLevel?: 'none' | 'mentioned' | 'used' | 'owned';
  relevance?: 'none' | 'weak' | 'partial' | 'high';
  backgroundRequirement?: 'preferred' | 'required';
  backgroundMatch?: 'none' | 'unrelated' | 'related';
  resumeEvidence?: string;
}
```

评分准入条件：

```text
isScoreable = true
且 dimension 属于六个能力维度之一
且具备完整、合法的评分字段
```

其中：

- 技能、经验、项目、成果使用 `requiredDepth`、`resumeEvidenceLevel`、`relevance`。
- 教育专业、行业领域使用 `backgroundRequirement`、`backgroundMatch`。

`isHard` 不决定是否参与评分，`dimension` 也不能替代 `isScoreable`。

---

## 4. `isHard` 与 `isScoreable`

两个字段相互独立：

| 示例 | `isHard` | `isScoreable` | 处理方式 |
| --- | ---: | ---: | --- |
| 必须在上海办公 | true | false | 只做硬性条件核查 |
| 必须接受出差 | true | false | 只做硬性条件核查 |
| 必须掌握 TypeScript | true | true | 硬性核查并参与技能评分 |
| 有 AI 项目经验优先 | false | true | 参与项目或行业能力评分 |
| 薪资福利说明 | false | false | 保留信息但不评分 |

### 4.1 学历、专业、年限和证书

采用“按能力性拆分”的规则：

- **最低学历**：作为硬性门槛核查；只有当它同时表达与岗位相关的教育能力时，才另建可评分项。
- **专业相关性**：可以进入教育专业维度评分。
- **最低工作年限**：作为硬性门槛核查；实际经历的责任深度、复杂度和相关性另建经验评分项。
- **必须证书**：作为硬性条件核查；如果证书本身能证明岗位需要的能力或成果，可以同时建立对应评分项。
- **地点、出差、到岗时间等条件**：通常只核查，不进入六维能力评分。
- **硬性技能要求**：既可以是硬性条件，也可以是对应能力维度的评分项。

同一事实可同时产生“门槛核查”和“能力评分”两个结果，但不得重复增加能力权重。

## 5. 要求拆分、合并与稳定标识

### 5.1 拆分规则

- 一个可以独立判断是否满足的能力对应一个要求项。
- 一句话包含多个互相独立的能力时可以拆分。
- “A 和 B 都必须”可以拆成两个独立要求。
- “A/B 任一即可”应作为一个选择型要求，只计权一次。
- “A 或同类工具”不得机械拆成多个必须项。

### 5.2 合并规则

- JD 中对同一能力的同义重复描述只计权一次。
- 合并后保留全部岗位原文来源，不丢失限定条件。
- 计算层不再自行推测同义项；AI 提取完成后必须通过重复项校验。
- 同一段原文不得无依据拆成多条重复增加权重。

### 5.3 稳定标识

- `requirementId` 不得使用数组位置。
- 相同规范化要求在同一份 JD 中必须得到稳定标识。
- 同一 JD 更换简历时，要求 ID、重要度、普通能力的要求深度、背景维度的背景要求档位和维度权重保持不变。
- 具体哈希规范在阶段 3 接入 AI 提取时实现并测试。

## 6. 固定映射表

### 6.1 岗位要求重要度

| 等级 | 系数 |
| --- | ---: |
| `core` 核心/必须 | 1.0 |
| `important` 明确要求 | 0.8 |
| `normal` 一般要求 | 0.5 |
| `bonus` 优先/加分项 | 0.3 |

### 6.2 岗位要求深度

只用于技能、经验、项目和成果：

| 等级 | 分数 |
| --- | ---: |
| `basic` 了解基础概念 | 40 |
| `familiar` 熟悉并可使用 | 60 |
| `practical` 能够独立实践 | 80 |
| `expert` 精通并能主导复杂任务 | 100 |

### 6.3 简历证据等级

只用于技能、经验、项目和成果：

| 等级 | 分数 |
| --- | ---: |
| `none` 未发现证据 | 0 |
| `mentioned` 仅提及或只出现在列表中 | 35 |
| `used` 在学习、工作或项目中实际使用 | 70 |
| `owned` 独立负责、主导或承担关键职责 | 100 |

`radar-v2` 删除 `achieved`。是否产生量化成果属于成果事实，应由成果维度和具体证据表达，不再混入“参与深度”档位。

### 6.4 证据相关度

只用于技能、经验、项目和成果：

| 等级 | 系数 |
| --- | ---: |
| `none` 无关或没有证据 | 0 |
| `weak` 弱相关 | 0.3 |
| `partial` 部分相关 | 0.7 |
| `high` 高度相关，可作为该证据等级的有效证明 | 1.0 |

阶段 2 二次人工校准决定：相关度保持四个固定档位，不允许 AI 在区间内直接输出任意小数。区间内插值作为后续可选优化，只有建立可追溯的岗位限定点和证据覆盖点后才能引入。

### 6.5 背景要求强度

只用于教育专业和行业领域：

| 档位 | 分数 |
| --- | ---: |
| `preferred` 相关背景优先 | 40 |
| `required` 必须具备相关背景 | 100 |

### 6.6 简历背景匹配

只用于教育专业和行业领域：

| 档位 | 分数 |
| --- | ---: |
| `none` 未发现背景证据 | 0 |
| `unrelated` 有背景，但与岗位要求不相关 | 15 |
| `related` 有与岗位要求相关的背景 | 100 |

教育专业和行业领域不使用 `requiredDepth`、`resumeEvidenceLevel` 或 `relevance`，不得将两套档位混用。

### 6.7 证据语义边界

- 传统前端开发必须有 JavaScript/TypeScript、React/Vue 等对应语言或框架的实际编码证据。
- 传统后端开发必须有服务端、API、数据库或 Node.js/FastAPI 等后端框架的实现证据。
- Vibe Coding、低代码、产品设计、架构规划和前后端接入/联调，可证明架构衔接、系统集成或工程化思维，不得替代传统前端或后端开发证据。
- 使用 Python 开发业务算法只证明 Python 使用经验；未实现服务端、API、数据库或后端框架时，不计为后端开发。
- 岗位限定的行业/业务系统经验，必须有建设或交付该领域业务系统的直接证据；不得仅根据“业务”“系统”“产品”等通用词判为相关。
- 市场敏感度、Owner 意识、平台化思维和业务闭环属于可评分能力，需用具体行为取证；抗压性不得仅由任务繁忙或项目复杂推测。

## 7. 目标计算公式

### 7.1 单项分数

技能、经验、项目和成果使用普通能力公式：

```text
单项岗位要求强度 = 岗位要求深度分
单项简历证据强度 = 简历证据等级分 × 证据相关度
单项要求覆盖度 = min(单项简历证据强度 ÷ 单项岗位要求强度, 1) × 100
```

教育专业和行业领域使用背景专用公式：

```text
单项岗位要求强度 = 背景要求强度分
单项简历证据强度 = 简历背景匹配分
单项要求覆盖度 = min(单项简历证据强度 ÷ 单项岗位要求强度, 1) × 100
```

例如：

- `preferred + none = 0%`
- `preferred + unrelated = 15 ÷ 40 = 37.5%`
- `preferred + related = 100%`（原始比值超过 100%，按上限截断）
- `required + none = 0%`
- `required + unrelated = 15 ÷ 100 = 15%`
- `required + related = 100%`

候选人的证据超过岗位要求时，单项覆盖度封顶 `100%`，不能抵消其他要求的缺口。

后端通过 `scoringMethod` 区分两套模型：

- `evidence_relevance` 表示普通能力公式。
- `background_match` 表示背景专用公式。为保持汇总结构统一，返回值中的 `requiredDepthScore` 承载背景要求强度分，`evidenceLevelScore` 和 `resumeEvidenceScore` 承载背景匹配分，`relevanceFactor` 固定为 `1`。前端必须根据 `scoringMethod` 展示对应术语，不得把背景分数误标为岗位深度或证据等级。

### 7.2 维度汇总

```text
维度重要度合计 = Σ该维度可评分要求的重要度
维度岗位要求强度 = Σ(单项岗位要求强度 × 单项重要度) ÷ Σ单项重要度
维度简历证据强度 = Σ(单项简历证据强度 × 单项重要度) ÷ Σ单项重要度
维度要求覆盖度 = Σ(单项要求覆盖度 × 单项重要度) ÷ Σ单项重要度
```

分母是该维度可评分要求的 `Σ重要度`，不是要求项数量。

例如技能维度有 7 条要求，重要度分别为：

```text
1.0、1.0、0.8、0.8、0.5、0.5、0.3
```

则：

```text
要求数量 = 7
重要度合计 = 4.9
维度加权平均的分母 = 4.9
```

### 7.3 维度权重

所有六维统一归一化，不设置最低或最高权重：

```text
维度精确权重 = 该维度可评分要求的重要度合计 ÷ 全部可评分要求的重要度合计
```

约束：

1. 权重只读取 JD 提取出的可评分要求和重要度。
2. 权重不读取候选人的简历证据、能力分、状态、优势或差距。
3. 教育专业和行业领域不设置 `15%` 或其他上限，与其他维度使用同一公式。
4. 只有一个有效维度时，该维度权重为 `100%`。
5. 没有要求的维度权重为 `0%`。
6. 内部使用精确小数；页面整数百分比采用确定性的最大余数法补差，确保显示合计为 `100%`。
7. 没有任何可评分要求时，不生成伪造的 `0` 分，返回“无可评分要求”状态。

### 7.4 综合能力匹配分

以要求项级别计算作为唯一主公式：

```text
综合能力匹配分 = Σ(单项要求覆盖度 × 单项重要度) ÷ Σ单项重要度
```

同时满足数学等价关系：

```text
综合能力匹配分 = Σ(维度要求覆盖度 × 维度精确权重)
```

阶段 2 已确认并验证两条路径结果一致。内部总分使用精确权重；显示用整数权重只负责展示，不参与内部总分计算。由于页面权重经过取整，用户用显示权重手算时极端情况下可能与内部结果产生约 1 分差异，页面必须说明这一点。

## 8. 状态与结果语义

### 8.1 能力状态

目标状态：

- `matched`：要求覆盖度达到阈值，且不存在核心要求完全缺失。
- `core_gap`：存在核心可评分要求完全缺失；保留正常计算的数值能力分，同时单独标红核心缺口，不对分数做隐藏封顶或归零。
- `partial`：存在证据，但覆盖度未达到匹配阈值。
- `missing_evidence`：当前范围所有可评分要求均无简历证据。
- `not_required`：岗位没有该维度的可评分要求。

具体匹配阈值暂沿用 `80%`，阶段 2 使用真实样本验证。状态不再只按缺失项数量判断。

### 8.2 三类结果必须分开

1. **硬性条件风险**：岗位明确要求的门槛是否满足、明确不满足或无法确认。
2. **能力差距**：简历有相关证据，但要求覆盖度不足。
3. **简历未发现证据**：当前简历没有可验证证据，不代表候选人不会。

三类结果不得继续混在一个语义含糊的 `gaps` 列表中。

### 8.3 优势和差距

```text
单项优势贡献 = 单项要求覆盖度 × 单项重要度
单项差距影响 = (100 - 单项要求覆盖度) × 单项重要度
```

- 核心缺口优先展示。
- 同分时按固定维度顺序和稳定要求 ID 排序。
- 返回具体要求项，不只返回维度名称。

## 9. 展示要求

页面应使用：

- 岗位要求强度。
- 简历证据强度。
- 要求覆盖度。
- 评分占比。
- 简历未发现证据。

每个维度至少展示：

- 要求项数量。
- 可评分项数量。
- 重要度合计。
- 评分占比。
- 岗位要求强度。
- 简历证据强度。
- 要求覆盖度。
- 对综合分的贡献。

每条要求支持展开查看岗位原文、简历证据、离散档位、映射数值和计算公式。

历史记录只有 `scoringVersion = radar-v2` 时才能展示新算法解释；旧记录不得根据旧总分伪造新六维数据。

## 10. 稳定性和失败边界

- AI 匹配提取使用 `temperature = 0`。
- 解析 AI JSON 前必须检查 `finish_reason`。
- `finish_reason = length` 时明确报告输出截断，禁止进入算分。
- 影响评分含义的非法枚举不得静默使用默认值。
- 岗位要求遗漏、重复 ID 或证据无法回查时，不得生成看似正常的分数。
- 同一规范化 JD 和简历版本使用包含模型、提示词版本与参数的输入哈希做一致性缓存。
- 同一 JD 更换简历时，岗位要求清单与维度权重保持不变。

---

## 11. 人工修正与补录重评

人工修正不得直接拖动雷达节点或覆盖最终分数，而应修改底层要求项或证据判断，并记录：

- 原识别档位。
- 修正后档位。
- 修正依据。
- 修正时间。
- 是否由人工校准。

补录保存后必须：

1. 更新简历内容和版本。
2. 更新岗位记录使用的简历快照。
3. 重新执行证据对齐。
4. 从单项结果开始完整重算。
5. 保存新的 `analyzedResumeId`、输入哈希与评分版本。
6. 同一 JD 的要求、重要度和权重保持不变。

## 12. 阶段 1 冻结结论

已确认：

1. 所有六维不设最低或最高权重，按 JD 可评分要求的重要度统一归一化。
2. 权重只根据 JD，不根据候选人简历证据。
3. 综合分采用要求项级别的重要度加权覆盖度。
4. `isHard` 和 `isScoreable` 相互独立。
5. 学历、专业、年限、证书等按能力性拆分，不机械地全部评分或全部排除。
6. 采用“岗位要求强度、简历证据强度、要求覆盖度、评分占比”等新术语。
7. 能力分与硬性条件分开显示，硬性条件不暗中扣减能力分。
8. 简历证据使用四档：`none=0`、`mentioned=35`、`used=70`、`owned=100`；删除 `achieved`。
9. 技能、经验、项目和成果的相关度使用四档：`none=0`、`weak=0.3`、`partial=0.7`、`high=1.0`；不允许 AI 输出区间内任意小数。
10. 教育专业和行业领域使用背景专用模型：岗位要求为 `preferred=40`、`required=100`，简历背景为 `none=0`、`unrelated=15`、`related=100`。
11. 内部总分使用精确权重，页面整数权重只用于展示。
12. 核心缺口保留正常计算分，并作为独立风险标红，不暗中封顶或归零。
