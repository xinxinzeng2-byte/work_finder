## 新增需求：岗位分析重新选择简历

### 需求目标

在岗位分析结果页点击“重新分析”后，以弹窗列出全部可用简历，明确区分“原始简历”和“定制简历”，并标注这条岗位当前分析实际使用的简历。用户选择简历后：

1. 选择的简历与本条岗位上次分析使用的简历及版本相同：直接复用已保存的完整分析结果，不重复调用 AI。
2. 选择的简历不同，或同一简历的版本已变化：使用选中的简历重新调用 AI 分析，并在成功后原子替换岗位分析结果。
3. 重新分析失败：保留原分析结果、原简历绑定和页面内容不变。
4. 选择定制简历只改变本条岗位的分析输入，不改变系统默认原始简历，也不改变简历库中的“当前默认”标记。

### 开发计划

- 在 `AnalyzeView` 增加重新分析简历选择弹窗，按原始/定制类型展示名称、版本、更新时间和当前使用标记。
- 以 `analyzedResumeId + analyzedResumeVersion` 作为复用判断；兼容没有绑定版本的历史记录，并回退到已保存简历快照。
- 将重新分析处理改为“先选择、再决策”：同简历直接复用，不同简历才调用 `analyzeMatchV2`。
- 保存新分析时同步更新 `resumeSnapshot`、`analyzedResumeId`、`analyzedResumeVersion`、评分版本和输入哈希。
- 增加渲染与选择逻辑的自动检查，并完成客户端构建。

## 一、当前问题

1. 当前维度权重存在 `5%—40%` 上下限和差额重分配，用户容易理解为事后调权；有效维度较少时还可能无法合计为 `100%`。
2. 页面中的“7 项技能、2 项教育专业”是要求项数量，不是重要度合计；当前没有展示权重的中间依据。
3. 岗位能力分和简历能力分采用重要度加权平均，分母是 `Σ重要度`，不是要求项数量；页面没有解释。
4. `isHard` 与“是否参与评分”混在一起，无法准确表达地点、出差、学历、技能等不同类型的要求。
5. AI 提示词对硬性要求是否进入六维证据存在冲突，后端也没有独立的 `isScoreable` 评分准入字段。
6. AI 同时输出证据、匹配状态和总结，与后端确定性算法职责重叠，可能出现状态或总结与分数冲突。
7. AI 决定要求拆分、维度和重要度；普通能力维度的岗位深度、证据等级和相关度，以及背景维度的背景要求和背景匹配，任一档位波动都会改变结果。
8. 当前匹配调用使用 `temperature: 0.3`、`max_tokens: 4096`，且未检查 `finish_reason`，输出截断可能只表现为 JSON 解析失败。
9. 当前状态判断部分依赖缺失项数量比例，没有充分体现核心要求和重要度。
10. 历史数据、重新分析和补录重评需要严格绑定简历版本与评分版本。
11. 现有单测覆盖不足，无法证明权重、总分、AI 契约和完整链路均可靠。

## 二、职责边界

### 2.1 AI 负责

- 从 JD 中识别独立、不重复的岗位要求。
- 判断维度、`isHard`、`isScoreable`。
- 从限定枚举中选择重要度；普通能力维度选择要求深度、证据等级和相关度，教育专业和行业领域选择背景要求和背景匹配档位。
- 返回岗位原文和简历原文摘录。
- 找不到证据时明确返回无证据，不推测候选人未写出的能力。

### 2.2 后端负责

- 校验 AI 输出是否合法、完整、不重复、可追溯。
- 将离散档位映射为固定数值。
- 计算单项分、六维汇总、维度权重、综合分和状态。
- 计算优势、核心缺口、能力差距和简历证据不足。
- 生成计算明细、版本信息和与算法结果一致的总结。
- 保证同一结构化输入得到相同结果。

### 2.3 前端负责

- 只展示后端结果，不重新计算业务分数。
- 展示要求数量、重要度合计、权重、分数和计算依据。
- 区分硬性条件、能力差距和简历证据不足。
- 按评分版本安全展示新旧历史数据。

## 三、建议的目标计算模型

> 以下是本计划的推荐方案。只有阶段 1 人工确认后，才成为正式开发口径。

### 3.1 双标签

```ts
isHard: boolean       // 是否属于必须满足的门槛
isScoreable: boolean  // 是否参与六维能力评分
```

| 例子 | `isHard` | `isScoreable` | 处理方式 |
| --- | ---: | ---: | --- |
| 必须在上海办公 | true | false | 只做硬性条件核查 |
| 必须接受出差 | true | false | 只做硬性条件核查 |
| 必须掌握 TypeScript | true | true | 既核查硬性条件，也参与能力评分 |
| 有 AI 项目经验优先 | false | true | 参与能力评分 |
| 薪资福利说明 | false | false | 保留信息但不评分 |

### 3.2 固定映射

| 类型 | 档位与数值 |
| --- | --- |
| 重要度 | `core=1.0`、`important=0.8`、`normal=0.5`、`bonus=0.3` |
| 岗位深度 | `basic=40`、`familiar=60`、`practical=80`、`expert=100` |
| 简历证据 | `none=0`、`mentioned=35`、`used=70`、`owned=100`；`radar-v2` 删除 `achieved` |
| 相关度 | `none=0`、`weak=0.3`、`partial=0.7`、`high=1.0`；保持四个固定档位 |
| 背景要求（教育/行业） | `preferred=40`、`required=100` |
| 背景匹配（教育/行业） | `none=0`、`unrelated=15`、`related=100` |

### 3.3 单项分数

```text
技能/经验/项目/成果：
单项岗位要求强度 = requiredDepth 对应分数
单项简历证据强度 = evidenceLevel 对应分数 × relevance 对应系数

教育专业/行业领域：
单项岗位要求强度 = backgroundRequirement 对应分数
单项简历证据强度 = backgroundMatch 对应分数

两类共用：
单项要求覆盖度 = min(单项简历证据强度 ÷ 单项岗位要求强度, 1) × 100
```

只有 `isScoreable=true` 且属于六维之一的要求参与能力评分。

### 3.4 维度汇总

```text
维度重要度合计 = Σ该维度可评分要求的重要度
维度岗位要求强度 = Σ(单项岗位要求强度 × 重要度) ÷ Σ重要度
维度简历证据强度 = Σ(单项简历证据强度 × 重要度) ÷ Σ重要度
维度要求覆盖度 = Σ(单项要求覆盖度 × 重要度) ÷ Σ重要度
```

分母使用 `Σ重要度`，不使用要求项数量。“技能 7 项”只表示共有 7 条技能要求。

### 3.5 维度权重

推荐取消 `5%—40%` 上下限和差额重分配：

```text
维度精确权重 = 该维度可评分要求的重要度合计 ÷ 全部可评分要求的重要度合计
```

规则：

1. 权重只由 JD 决定，不读取简历分数或匹配状态。
2. 同一 JD 更换简历后权重不变。
3. 只有一个有效维度时，该维度权重为 `100%`。
4. 没有要求的维度权重为 `0%`。
5. 内部保留精确小数；页面整数百分比使用确定性的最大余数法补差，显示合计严格为 `100%`。
6. 没有可评分要求时返回明确空状态，不用 `0` 分冒充有效结果。

### 3.6 综合能力匹配分

推荐以要求项为唯一主计算路径：

```text
综合能力匹配分 = Σ(单项要求覆盖度 × 单项重要度) ÷ Σ单项重要度
```

六维只负责归组展示。该结果应与“维度覆盖度 × 维度精确权重”的聚合结果数学等价。

### 3.7 硬性条件

能力分和硬性条件分开显示：

```text
能力匹配分：91 / 100
硬性条件：3 项满足、1 项待确认、1 项明确不满足
推荐结论：存在硬性条件风险
```

硬性条件不暗中扣减能力分。若未来设计统一推荐指数，必须另立公式并明确展示调整原因。

### 3.8 页面术语

| 当前名称 | 建议名称 |
| --- | --- |
| 岗位能力 | 岗位要求强度 |
| 简历能力 | 简历证据强度 |
| 匹配度 | 要求覆盖度 |
| 岗位权重 | 评分占比 |
| 未发现 | 简历未发现证据 |

# 阶段 1：冻结规则、样本与测试基线

## 目标

一次性确定产品和算法口径，并建立后续开发共同使用的验收样本，避免边开发边改公式。

## 开发子内容

### 1.1 冻结字段与边界

- 明确定义 `isHard`、`isScoreable`、`dimension`、`importance`、`requiredDepth`、`resumeEvidenceLevel`、`relevance`、`backgroundRequirement`、`backgroundMatch`。
- 明确岗位要求强度、简历证据强度、要求覆盖度、评分占比和综合分。
- 明确“简历未发现证据”不等于候选人不会。
- 明确硬性条件状态：`met`、`not_met`、`unknown`、`not_applicable`。

### 1.2 冻结要求拆分与去重规则

- 一个独立能力对应一个要求项。
- 同义重复要求只计权一次，但保留全部原文来源。
- 复合要求只有各部分可独立判断时才拆分。
- 区分“A/B 任一即可”“A 和 B 都必须”“A 或类似工具”。
- 同一原文不得无依据拆成多项增加权重。
- 稳定 ID 不使用数组位置；具体生成规则写入算法说明。

### 1.3 冻结评分规则

- 确认取消维度 `5%—40%` 限制及差额重分配。
- 确认采用要求项级别总分。
- 确认四套离散映射是否保持现值。
- 确认学历、专业、工作年限、地点、证书、技能的默认 `isHard/isScoreable` 规则。
- 确认相关度先保持乘法，还是直接调整；若暂不调整，明确阶段 2 必须用样本校准。
- 确认教育专业和行业领域采用背景要求与背景匹配专用模型，不使用普通能力档位。
- 确认能力分与硬性条件独立展示。
- 确认页面术语。

### 1.4 建立测试基线

记录当前固定输入下的：

- 六维岗位分、简历分和权重。
- 六维状态与综合分。
- 优势和差距。
- 当前评分版本。

基线用于说明新旧变化，不代表旧算法正确。

### 1.5 建立黄金样本

至少准备 15 组脱敏样本：

1. 单一技能要求且完全匹配。
2. 单一技能要求且无证据。
3. 只有一个可评分维度。
4. 只有两个可评分维度。
5. 六维均有要求。
6. 核心要求缺失、加分项满足。
7. 核心要求满足、多个加分项缺失。
8. 地点等硬性但不评分要求。
9. 技能等硬性且评分要求。
10. 同一能力在 JD 中重复出现。
11. “A/B 任一即可”的选择型要求。
12. 一句话包含多个独立要求。
13. 简历只有技能列表，没有经历证据。
14. 简历有高度相关但不完全对应的迁移经验。
15. 补录经历前后重新评分。

另准备至少 3 组等价 JD：内容相同但排序、段落或项目符号不同。

### 1.6 建立测试入口

- 增加可重复执行的评分测试脚本。
- 优先使用现有 Node、TypeScript 和 `ts-node`，不新增依赖。
- 区分纯算法单测、AI 契约测试和集成测试，算法单测不得依赖实时 AI。

# 阶段 2：重构数据结构、校验与确定性算法




### 2.2 严格校验

- 校验维度和重要度；普通能力维度校验深度、证据等级和相关度，背景维度校验背景要求和背景匹配枚举。
- 校验要求 ID 唯一。
- 校验岗位原文可追溯。
- 正向简历证据必须有简历摘录。
- 没有简历原文时，普通能力的证据等级与相关度强制为 `none`，背景维度的背景匹配强制为 `none`，并产生告警。
- `isScoreable=true` 时必须属于六维之一并具备评分字段。
- 影响评分的非法字段不得静默默认成 `normal` 或 `familiar`。
- 统一要求列表作为唯一事实源，其他状态列表由算法派生。

### 2.3 实现纯函数算法

建议拆分：

- `calculateRequirementScore`
- `calculateDimensionSummary`
- `calculateDisplayWeights`
- `calculateOverallScore`
- `calculateStatuses`
- `rankAdvantagesAndGaps`
- `calculateCapabilityRadarV2`

### 2.4 修复权重

- 删除 `5%—40%` 上下限。
- 删除循环式差额重分配。
- 使用重要度合计直接归一化。
- 内部使用精确权重。
- 页面整数权重用最大余数法补差，显示合计为 `100%`。
- 无可评分项时返回明确空状态。

### 2.5 重算分数和状态

- 单项、维度和总分按第三章公式实现。
- 要求项总分与维度聚合结果必须等价。
- 能力超额时覆盖度封顶 `100%`。
- 建议状态：`matched`、`core_gap`、`partial`、`missing_evidence`、`not_required`。
- 如果前端暂不扩充状态，至少增加 `hasCoreGap`，不得只按缺失项数量判断。

### 2.6 优势和差距

```text
单项优势贡献 = 单项覆盖度 × 单项重要度
单项差距影响 = (100 - 单项覆盖度) × 单项重要度
```

- 核心缺口优先。
- 同分使用固定维度顺序和稳定 ID 排序。
- 返回具体要求项，不只返回维度名。

### 2.7 测试矩阵

- 输入换序不变、同输入重复至少 100 次不变。
- 合法随机输入的分数范围、权重总和及两条总分路径等价。
- 相关度不同计算方案在真实样本上的对比结果。
- 教育专业和行业领域的背景要求两档、背景匹配三档及全部组合。

# 阶段 3：重构 AI 提取并接入完整后端链路

## 目标

让 AI 只提供可追溯的结构化判断，并让本地 Express 与 Vercel Serverless 共用同一套校验和算法。

## 开发子内容

### 3.1 两阶段 AI 任务

#### A. 岗位要求标准化

输入 JD，输出：

- `requirementId`
- `title`
- `requirement`
- `jobEvidence`
- `dimension`
- `isHard`
- `isScoreable`
- `importance`
- `requiredDepth`
- `backgroundRequirement`
- 原文位置或来源索引

#### B. 简历证据对齐

输入冻结后的要求清单和简历，逐项输出：

- `requirementId`
- `resumeEvidenceLevel`
- `relevance`
- `backgroundMatch`
- `resumeEvidence`
- 无法判断原因

同一 JD 更换简历时复用岗位要求清单和权重。

### 3.2 移除 AI 评分职责

AI 不得输出或决定：

- 最终分数、岗位分、简历分、覆盖度和权重。
- `matched/partial/missing` 等算法状态。
- 优势和差距排序。
- 推荐投递结论。

### 3.3 提示词与契约

- 每个独立要求恰好出现一次。
- 同义要求合并，复合要求按阶段 1 规则拆分。
- `isHard` 与 `isScoreable` 分别判断。
- 所有档位只能来自限定枚举。
- 所有判断绑定原文。
- 简历没写时返回 `none`，不得推测。
- JSON 解析后继续执行严格业务校验。

### 3.4 稳定性与截断

- 匹配提取 `temperature` 调整为 `0`。
- 根据黄金样本压测确定 `max_tokens`，不凭猜测固定。
- 解析前检查 `finish_reason`。
- `finish_reason=length` 时明确返回输出截断，禁止进入 `JSON.parse` 和算分。
- 网络、格式或契约错误只做有限次数、可观测的重试。
- 使用 SHA-256 输入哈希做缓存或一致性复用。
- 缓存键包含模型、提示词版本、JD、简历版本和提取参数。

### 3.5 证据与要求完整性

- 要求 ID 重复、遗漏或无法映射时拒绝评分。
- 岗位摘录无法回查 JD 时标记失败或待核验。
- 简历摘录无法回查时不得保留正向证据等级、相关度或背景匹配档位。
- 区分 `unknown` 和 `none`，避免“无法判断”被误报为“不满足”。

### 3.6 共用后端链路

统一流程：

```text
请求校验
→ JD 要求标准化
→ 简历证据对齐
→ 结构校验
→ radar-v2 算分
→ 派生硬性条件和能力列表
→ 生成一致性总结
→ 返回并保存版本化结果
```

- `api/match.ts` 与本地 Express Controller 只做协议适配，不复制算法。
- 保存 `analyzedResumeId`、JD/简历快照、输入哈希、提取版本、评分版本、结构化证据和算法结果。
- 区分输入缺失、API Key 无效、AI 请求失败、输出截断、JSON 非法、契约失败、无评分项和算法异常。
- 总结在算分后生成；如由 AI 润色，不得修改数字、状态和排序。

# 阶段 4：前端解释、历史兼容与补录重评

## 目标

让用户能直接看懂权重和分数来源，同时保证旧记录、重新分析和补录重评不混用版本或简历快照。

## 开发子内容

### 4.1 六维摘要

每个维度展示：

- 要求项数量。
- 可评分项数量。
- 重要度合计。
- 评分占比。
- 岗位要求强度。
- 简历证据强度。
- 要求覆盖度。
- 对综合分的贡献。

### 4.2 权重解释

支持展开查看：

```text
技能评分占比 40%
= 技能重要度合计 4.0
÷ 全部评分项重要度合计 10.0
```

并逐项展示重要度，例如：

```text
TypeScript：核心要求 1.0
React：核心要求 1.0
Node.js：明确要求 0.8
数据分析：一般要求 0.5
AI 经验：加分项 0.3
```

明确提示：要求数量不是权重分母。

### 4.3 单项计算解释

每条可评分要求展示：

- 岗位原文和简历证据。
- 重要度与系数。
- `scoringMethod=evidence_relevance` 时展示岗位深度与分数、证据等级与分数、相关度与系数。
- `scoringMethod=background_match` 时展示背景要求档位与分数、背景匹配档位与分数，不展示普通能力的三个档位。
- 单项覆盖度。
- 对总分的贡献。

### 4.4 三类结果分区

分别展示：

1. 硬性条件：满足、明确不满足、待确认。
2. 能力差距：有证据但覆盖不足。
3. 简历未发现证据：当前简历无明确材料，可进入补录。

不得继续用一个含糊的 `gaps` 列表混合三种语义。

### 4.5 历史版本兼容

- `radar-v1` 只按旧规则展示。
- `radar-v2` 才展示新权重和单项公式。
- 缺少版本的数据按旧版本处理，不能猜成新版本。
- 没有真实六维数据时显示重新分析入口，不生成伪造数据。
- 提取失败、截断或无评分项时不展示半成品分数。

### 4.6 重新分析

- 优先使用 `analyzedResumeId` 与已保存简历快照。
- 对应简历不存在时明确要求选择当前简历或取消。
- 成功后原子替换完整匹配结果，不只替换总分。
- 失败时保留原记录。

### 4.7 补录重评

保存补录后：

1. 更新简历内容和版本。
2. 更新岗位关联的简历快照。
3. 重新执行证据对齐。
4. 从单项开始完整重算。
5. 保存新的 `analyzedResumeId`、输入哈希和评分版本。
6. 同一 JD 的岗位权重保持不变。

## 七、主要风险

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| AI 对同一 JD 的拆分不稳定 | 权重随排版变化 | 两阶段提取、温度归零、稳定 ID、去重校验、等价 JD 样本、输入哈希缓存 |
| 档位稳定但不符合业务直觉 | 分数可复现但不合理 | 真实黄金样本、相关度对比、人工手算后再接入 |
| 新旧数据混用 | 历史分数和解释错误 | `scoringVersion` 分支、旧数据只读兼容、重评显式升级 |
| AI 输出被截断 | JSON 失败或半成品算分 | 检查 `finish_reason`、token 压测、严格校验、失败阻断 |
| 补录仍使用旧快照 | 重评结果不变化 | 更新简历版本、快照、`analyzedResumeId` 和输入哈希 |
| 双层加权难解释 | 用户认为重复计算 | 要求项级别总分作为唯一主公式，六维只做等价归组 |

## 八、完成定义

本改造只有在以下条件全部成立时才算完成：

1. 每条岗位要求都有稳定 ID、岗位原文、评分边界和合法档位。
2. 每条正向简历证据都能回查原文或已保存的结构化经历。
3. 权重只由 JD 可评分要求的重要度决定，与简历无关。
4. 只要存在可评分要求，六维展示权重合计恒为 `100%`。
5. 要求数量与重要度合计分别展示。
6. 综合分能由单项明细手工复算。
7. 硬性条件、能力差距和简历证据不足分别表达。
8. 同一结构化输入重复计算结果相同。
9. AI 输出截断、非法或不完整时不会产生分数。
10. 历史记录、重新分析和补录重评均绑定正确简历版本与评分版本。
11. 全部 AI 自动验收通过。
12. 全部人工验收由用户明确确认。

第 12 项完成前，只能声明“开发与自动验证完成，等待人工验收”。
